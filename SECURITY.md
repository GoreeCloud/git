# Security policy and operating boundaries

This is an early-development, single-owner self-hosted service. **Do not deploy it as a public, multi-user Git forge** without an independent threat review.

- Source repository `GoreeCloud/git` is public. Never commit private Git objects, token files, SSH keys, backups, user data, `.env` files, or server configurations with secrets.
- Private repositories live only in a separate filesystem data root with owner-only `0700` permissions on the root, `repos/`, and each bare repository directory. Every repository access rechecks that repository's directory mode and refuses `HEAD` or `config` control-file symlinks instead of following them or silently chmodding restored data. The public source tree is never the repository storage root. Repository creation now atomically reserves an owner-only directory before Git initialization; incomplete reserved directories are not listed as repositories and are deliberately not deleted automatically. `gcgit doctor` also reports incomplete creation reservations, invalid managed entry names, unsafe links and overexposed repo modes without mutating them; ordinary `gcgit list` intentionally excludes incomplete repos. This is a basic preflight, not a Git-object integrity or encrypted backup test. Same-UID adversaries and filesystem race attacks outside this boundary remain unresolved.
- Git transport is standard Git-over-SSH. Use SSH public-key authentication and a dedicated non-root operating-system account. Select either a reviewed `git-shell` installation **or** a `gcgit serve-ssh` per-key forced-command installation; these approaches have different login-shell requirements. Manage key revocation through `authorized_keys`/your SSH infrastructure.
- This application does not implement a remote identity service, an ACL/organization model, Git LFS, branch policies per user, CI runners, hooks isolation, or an HTTP Git transport. Do not infer those features.
- The optional browser is Git-data read-only; its non-secret appearance preference updates require a Basic-authenticated POST with a token-derived HMAC CSRF check and reject cross-origin submissions when Origin is present. All Git repository state is unchanged by this settings form. The browser requires owner Basic authentication using a locally stored high-entropy token. It only binds to loopback; use an SSH tunnel or a separately configured TLS reverse proxy with proper access controls for remote viewing. Browser Basic auth may cache credentials. The HTTP server now permits only eight concurrent in-flight request workers and uses a ten-second socket timeout. Requests beyond capacity get generic 503 with no private metadata. Unsupported HTTP methods return safe denial responses with no-store/security headers; only the authenticated CSRF-protected POST appearance endpoint changes the non-secret UI preference. These limits do not bound costly Git metadata work, total requests over time, or access through a wrongly configured proxy.
- Browser appearance uses a separate non-sensitive SameSite=Strict/HttpOnly persistent cookie. Light is the default, and only authenticated requests may change appearance. Its authenticated POST form changes a presentation preference **only** with HMAC CSRF protection: GET requests never change settings, and there are no remote Git mutations or filesystem settings writes. CSP permits self-hosted form actions but continues to block script execution and external resources. This cookie is not an authentication credential. Browser cookies are host-scoped, not port-scoped: another service on the same hostname may receive this non-secret preference. Use a dedicated hostname if strict application isolation is needed. See [GC UI consumer acceptance](docs/gc-ui-consumer.md).
- The web token is readable by the server operating-system account and must be protected from backups, accidental copying, and logging. Rotating it requires restarting the web service. Use short-lived SSH forwarding rather than exposing an HTTP port to the Internet.
- CLI/web metadata and SSH Git subprocesses now use an explicit minimal environment, resolving Git only from the platform's trusted system path rather than trusting caller PATH, LD_*, PYTHONPATH, shell startup overrides, or arbitrary GIT_* variables. SSH may forward only the exact safe `GIT_PROTOCOL=version=2` hint. The interpreter/launcher environment is outside this child-Git boundary and must be secured separately by OpenSSH account policy. CLI and web metadata Git subprocesses also have a one-mebibyte captured-stdout ceiling, strict elapsed-time budget and fail-closed cleanup on timeout/overflow. Git stderr is discarded instead of exposing private paths. These are safeguards against memory growth from oversized refs or commit metadata, not global storage quotas, CPU admission controls, or a guarantee that all same-UID descendants can be contained. Native SSH Git transport is separately streaming and has its own bounded limits.
- Git hooks and pushed content should be treated as untrusted. Never automatically execute hooks from untrusted repositories in privileged contexts. Use a non-root service account.
- Maintain off-site encrypted backups of the private repository storage and periodically test restores. No backup automation is provided in this version. An **opt-in** disposable, local encrypted Kopia CLI restore acceptance harness is available at `scripts/smoke-kopia-git-recovery.py` and requires an independently reviewed external Kopia executable; it does not install binaries or operate on real private data, and does not prove off-host or GoreeCloud Backup alpha API recovery. A **separate opt-in** `scripts/smoke-backup-api-git-recovery.py` exercises the real loopback-authenticated Backup alpha control plane plus Kopia on only synthetic data in an operator-provided offline sandbox; it proves local API-to-engine restore wiring, **not** off-host or production disaster recovery. [Backup integration/recovery plan](docs/backup-recovery.md) explicitly reuses GoreeCloud Backup/Kopia and requires isolated restore acceptance, not unencrypted file sync. Backups of the private root may contain the web-token file; protect ciphertext/credentials and rotate a restored token before service use.
- Do not expose port 8787 publicly, weaken filesystem modes, or share a dedicated SSH account among untrusted users.

For real-host `sshd` account, key, host-key, firewall, and rollback acceptance, review [OpenSSH staging and security acceptance](docs/ssh-host-acceptance.md). The optional synthetic Linux `sshd -T` smoke test checks parsed configuration without starting a daemon. A separate **opt-in** `scripts/smoke-sshd-live.py` drill runs real OpenSSH inside disposable user/mount/network namespaces and tests host-key-pinned clone, denied unknown/wrong keys, denied shell/cross-repo/read-only writes, and explicitly authorized writes. Its synthetic root UID mapping forces `StrictModes no` **inside that isolated fixture only**. A separate opt-in `scripts/smoke-sshd-strict.py` fixture now uses a private temporary filesystem root, a **synthetic non-root** `gcgit` user and effective `StrictModes yes`; it additionally rejects unsafe key-directory permissions and revoked test keys. Neither fixture proves authorization/ownership for an actual persistent service account, public network safety, encrypted disaster recovery or production readiness.

Report vulnerabilities privately to the repository owner. Do not publish exploitation details or credentials in a public issue.
## Optional forced-command SSH restrictions (development)

- `gcgit --root PRIVATE_DIR serve-ssh --repo NAME` accepts only Git upload-pack for that named repository by default. `--allow-push` additionally enables receive-pack for that **one** repository. Unsupported verbs, extra arguments, malformed paths, cross-repo accesses, and missing `SSH_ORIGINAL_COMMAND` fail closed.
- Invoke it **only** as a trusted OpenSSH `authorized_keys` forced command with `restrict` on the corresponding key. It is not an authentication server; local processes with the service account's privileges can still access its repositories.
- OpenSSH runs a forced command via the user's configured login shell. A login shell of `git-shell` will **not** launch a custom Python forced command; use a separately reviewed shell + SSH configuration if selecting this mode. Do not allow unrestricted keys, password-based logins, PTY, port forwarding, X11 forwarding, or arbitrary shell sessions for this service account.
- Enforce per-key authorization and key rotation outside this application. A write-enabled key can push any allowed fast-forward ref to the named repository; this is not a branch-level ACL, and pushed objects must remain untrusted data.
- New bare repositories impose a Git `receive.maxInputSize` ceiling of 1 GiB per incoming pack stream by default, configurable from 1–16384 MiB at `gcgit create` time. This does **not** limit total repository growth, repeated small pushes, Git housekeeping, disk space, or existing repositories (which are not silently migrated). Host filesystem quotas and monitoring remain required.
- Forced-command Git transport has bounded default session time (600 seconds), CPU limit (300 seconds per child process), and virtual memory limit (2048 MiB per process). The Git subprocess is launched in its own POSIX process group and killed on wall-clock timeout. Explicit CLI options allow bounded adjustments. CPU and memory limits do **not** bound aggregate descendant resource use, Git pack disk growth, concurrent SSH sessions, or other user processes. Server-level quotas, cgroups, rate limits and audit trails remain required for a production service.
- Tests use a local simulated SSH transport; they do not establish server-level protection, identity verification, complete denial-of-service resistance, host firewall rules, or production readiness.
